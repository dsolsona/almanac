## Outcome and non-goals

`make run` and `make start` build the current checkout using Docker's cache before
starting the app, so ordinary startup cannot silently serve an old image after
source changes. `make bootstrap` follows the same path without duplicate builds.
Keep Docker Compose and Make as the only host prerequisites. Do not change product
authentication, reset data, add dependencies or introduce arbitrary passthrough.

## Required context

AGENTS.md, testing strategy, SPEC-0013 local workflow, F1-T19, Makefile, Dockerfile,
compose.yaml and the existing Compose/cancellation acceptance scripts. Reuse the
prepared isolated worktree; do not reinstall tools without evidence of a gap.

## Interfaces and edit scope

Edit Makefile, README, local workflow spec/plan, applicable guidance and existing
Compose acceptance scripts. Validate the configured port before build/start side
effects. A failed build returns failure, preserves an already-running old app,
and never prints readiness. Use the existing cached Compose build; no --no-cache.
Do not delete volumes or expose credentials. Retain explicit migration, readiness,
initializer, loopback-port, cancellation and occupied-port behavior.

## Acceptance and expected cases

1. Daily run on a fresh prepared source builds the app if no image exists; no
   separate bootstrap prerequisite is needed. The start alias behaves identically.
2. A changed source fixture yields changed served assets after `make run`.
   Mutate only a test-owned copy of the build context; never maintainer source.
3. Unchanged source uses the Docker build cache. Bootstrap builds once per call.
4. Existing administrator login, data and protected secrets survive run/start;
   PostgreSQL container identity remains stable as in the current acceptance case.
5. Invalid ports fail before changing the stack; build failure cannot stop the
   current healthy app or report success. Existing cancellation/cleanup and port
   collision expectations remain enabled.
