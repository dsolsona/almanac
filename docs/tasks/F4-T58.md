# F4-T58: Compare the measured populations on SLO detail

- Status: review
- Governing contracts: [SPEC-0016](../specs/0016-maintenance-exclusions.md)
  and [SPEC-0020](../specs/0020-cumulative-slo-calculation.md)
- Implementation plan: [0046](../plans/0046-maintenance-management.md)
- Dependency: [F4-T56](F4-T56.md)
- Worktree: `.worktrees/maintenance-comparison` on `codex/maintenance-population-comparison`

Present the reported eligible population and a comparison including maintenance
events, both from one operational evaluation. Use its server-provided excluded
counts, distinguish unknown excluded observations, and leave attainment unavailable
when the compared population has no events. The comparison explains the current
calculation and does not change the graph series, compliance outcome, or alert data.

Use exact decimal arithmetic and the calculation contract's half-even output
rounding. Verify the independent documented example and the browser's comparison
from the ordinary HTTPS backend with intentionally failed observations inside a
maintenance interval.

The three focused comparison tests passed in 1.17 seconds, including exact
rounding and unknown populations. The isolated browser journey passed in 26.6
seconds, or 29.6 seconds including onboarding. It observes a real collector,
adds fixture-only retained observations, and verifies 297 / 300 eligible
events (99%) against 297 / 400 including maintenance (74.25%) through the
ordinary backend and UI. See the
[deployed comparison](../design/mocks/maintenance/production/maintenance-population-comparison.png).
The first browser run verified the backend counts and then timed out on
an exact-text selector that omitted the disclosure's interval count.
The combined maintenance browser selection reproduced two windows with the
same title. The list assertion now matches both the accessible title and the
scheduled window's own link. The comparison and scheduling journeys both
passed together with onboarding in 37.1 seconds of Playwright time.

The shared deployed suite can already have a healthy service from the
comparison journey when the service graph test filters for On track. The
failed trace showed the expected healthy Checkout node. The graph test
now verifies the actual matching service IDs and checks the empty state
when the saved catalog has no matching service. Comparison, all three
service journeys and onboarding passed together in 39.0 seconds.
