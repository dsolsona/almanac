## Outcome and reproduction

Reduce measured overview-query work while preserving exact per-request groups,
live keyset order/filtering, stale/unavailable classification and authentication.
The prior 200-SLO contention workload has overview p95 1,564 ms; one 1,289-ms
server trace spends 931 ms in ListSloOverviewPage and 250 ms in CountGroups, with
45 ms pool acquisition. A post-load literal plan (38-ms planning, 16-ms execution)
does not reproduce prepared statements, concurrent execution or serialization.

The ordinary user opens the SLO list, filters/groups or changes pages and receives
correct rows/counts, including currentness and missing-data states, within existing
budgets. Forward/back navigation must remain valid as rows move. Revoked authority
must still fail. No UI redesign, pool/timeout increases or relaxed budgets.

## Plan and scope

1. Seed the isolated 200-SLO E2E fixture and preserve its stack/reports. Measure exact
   generated prepared SQL with application settings, automatic/custom/generic plans,
   repeated execution, serialization and concurrent readers before choosing a fix.
2. Add a focused real-database regression for the reproduced excess work or semantic
   risk. Inspect existing live keyset/currentness tests and independent expectations.
3. Apply the smallest query/source correction supported by evidence; regenerate
   SQLC. Production changes belong to overview query sources and their direct
   storage consumers, with schema changes only if measured evidence requires them.
4. Run focused real-database correctness and measured-query checks, then the affected
   real-container overview journey/workload. Preserve failed runs and report remaining
   broader contention gates separately from this correction.

## Fixture storage correction

The first full contention run failed and is retained. Host resource inspection
then identified a distinct fixture-capacity problem: the E2E PostgreSQL tmpfs uses
895 MiB of base data and 1,008 MiB of WAL on a 3,939 MiB VM with no swap. Its cgroup
holds 2,147,020,800 bytes of shared memory. Normal Docker-backed persistence does
not require all these database files to remain in RAM. The primary agent authorized
an opt-in disk volume for this long experiment; normal suite defaults stay unchanged.

Stopped only this fixture's agent/application, created a private 74.6-MB
custom-format dump (7.226 s), verified its directory and fully decoded its contents
(1.267 s) before replacing the mount. Restoring to the project-owned disk volume
took 10.861 s. Exact SLO/observation/projection counts and good/total sums match
before and after; the same application became healthy in 5.338 s and its agent
resumed. Credentials, reports and traces remain preserved. The
[storage evidence](../evidence/slo-overview-performance/storage-isolation.json)
records the archive hash and memory recovery from 90–764 MiB available to 2,668 MiB.

`E2E_POSTGRES_STORAGE=disk` selects the opt-in overlay through shared shell and
TypeScript Compose arguments, including asynchronous SQL. Profiles now record
storage mode and overlay/helper hashes. Reusing prior backfill requires a fresh,
separately identified measurement fixture before another capacity claim. No new
timing run starts before resource stability and the coordinated UI verification
gap. Budgets, CPU/RAM, timeouts and connection limits do not change.

Configuration/import/JSON checks and the documentation checker pass in 2.023 s;
the checker covers 236 Markdown files and 1,776 local links. The normal Compose
configuration still selects tmpfs and the opt-in selects the named volume; invalid
storage values fail before invoking Docker. Full failure-report statistics confirm
one failed test over 362.268 s. A single bulk trace export exceeded VictoriaTraces'
51-MB sort budget; bounded time slices preserved 361,679 records instead, without
changing the server limit. The private dump, copied failure report/results and
21-MiB compressed trace export remain outside version control.
