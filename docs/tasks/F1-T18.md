## Screen contract

Export `AuthPage` with optional injected `client: ReturnType<typeof createAuthClient>`
for component checks; the production default uses the same-origin client.
Use the existing masthead/wordmark, shared ThemeToggle, Button, TextField, Panel and
LoadingIndicator. Feature CSS composes existing tokens and controls; no parallel
design system. Keep one main landmark, skip link, meaningful page heading, visible
labels, associated field errors, focus on changed state/error, and no horizontal
overflow at 360px. Theme remains usable during loading/errors.

On mount, read context once. Render loading while pending, sign-in for anonymous
context, password setup for a restricted session, or signed-in identity for a normal
session. A failed initial context shows an unavailable page with explicit Check
again; never invent an anonymous or authenticated state. Abort in-flight work on
unmount and prevent stale results from updating a newer state. No background
polling, automatic mutation retry, artificial loading delay or success timeout.

Use these visible headings and labels for predictable acceptance checks:

- Anonymous: heading Sign in; fields Login and Password; submit Sign in.
- Restricted: heading Set your permanent password; fields Current password,
  New password and Confirm new password; submit Set password; Sign out action.
- Normal: heading Signed in; show server-provided login and role as text; Sign out.
- Context unavailable: heading Unable to check your session; Check again action.

Use native forms and Enter submission. Guard synchronously against duplicate
submission; pending disables affected actions. Login is nonempty and at most256
UTF-8 bytes. Passwords are never trimmed. Current/sign-in password is nonempty and
at most512 UTF-8 bytes; new password is15–128 Unicode code points and at most512
UTF-8 bytes, differs from current, and matches confirmation. Do not impose ASCII
composition rules or HTML maxlength128 (which counts UTF-16 units). The backend
remains authoritative for policy/denylist checks. Use appropriate username,
current-password and new-password autocomplete values.

Clear password fields after an actual submission, whether successful or failed;
never retain the sign-in password for the next screen. Restricted reload asks for
current password again. Only explicit successful password response announces
completion. Logout success clears local identity and explicitly refreshes anonymous
context so a later login has valid CSRF; refresh failure shows unavailable.

Errors are locally authored safe messages, not server/network text. A definitive
rejection leaves the relevant form available and displays retry guidance for429
without automatically retrying. For expired-session/CSRF/conflict rejections, an
explicit Check session action can obtain fresh context; do not silently repeat the
original form. Keep credential rejection non-enumerating.

Unknown login/password outcome displays a persistent alert explaining the action
may have completed and was not repeated. Use validated recovery context if supplied
to render the appropriate form/identity beneath it; otherwise show Check session.
This read never clears uncertainty or claims password completion. If anonymous,
explain deliberate sign-in and that a changed password may already be active. No
automatic logout or other follow-on mutation. Only a subsequent deliberate action
can replace the message. A failed logout must not claim sign-out; offer Check
session, keep uncertainty visible, and do not automatically replay logout.

Never store credentials, CSRF or session state in browser storage/URL, or log them.
Only the existing theme preference is persisted. Do not add traces, analytics or
error diagnostics containing inputs. React text rendering escapes identity values.
