# F4-T59: Edit a scheduled maintenance window

- Status: review
- Governing contracts: [SPEC-0016](../specs/0016-maintenance-exclusions.md)
  and [F4-T53](F4-T53.md)
- Implementation plan: [0046](../plans/0046-maintenance-management.md)
- Dependency: [F4-T57](F4-T57.md)
- Worktree: `.worktrees/maintenance-browser-edit` on `codex/maintenance-browser-edit`

Editors and administrators can open the same context, scope and schedule form
from a current scheduled window. Selected objectives and exact UTC bounds
carry forward. An unrelated edit preserves the seconds and duration of
windows created through the API. A stale save retains the draft and allows the
operator to inspect the current revision before explicitly trying again.
Once maintenance starts, the detail page offers its lifecycle operations.

The three focused scheduling tests cover server-time status transitions, leaving
a scheduling form while a write is pending, and preserving an API-created
one-second window while editing its reason. The deployed browser journey
checks the prefilled affected SLO, saves a new revision, and verifies that
the UTC bounds and scope stayed the same.

The conflict regression swaps the sole affected SLO and changes the current
reason while a second editor holds a draft. The edit form shows the current
name, reason and schedule, plus the SLOs unique to each scope. Save remains
disabled until the editor chooses **Keep my draft**. That focuses **Save
schedule**, and the next request uses the reviewed revision's ETag.
[Deployed screenshot](../design/mocks/maintenance/production/maintenance-edit-conflict.png).

The new regression failed against the count-only review. All four focused
form tests and TypeScript passed in 5.29 seconds including container startup.
The deployed comparison passed in 26.9 seconds. The first edit-journey run
used a locator that omitted the service name from the SLO row. The next run
reached the later cancellation scenario with a stale fixture ETag after the
new edit. With both fixture issues corrected, the deployed edit and lifecycle
journey and onboarding passed in 7.6 seconds, or 62.8 seconds including stack
startup and cleanup.

The regular CI run also failed in `TestIntegrationExecutableFirstObjectiveJourney`
when the test subprocess exited before readiness. The original logs omit its
startup stage. Occupying the released HTTPS port during fixture setup reproduced
the same readiness failure and the backend logged a listener failure. The test
fixture now retains its HTTPS and metrics port reservations through setup and
releases them immediately before launching the executable. A future early exit
reports the exit code and a fixed startup diagnostic. The focused executable
journey passed with the race detector in 24.0 seconds after the change, or 28.6
seconds including the development container and test build.

Opening Edit schedule moves keyboard focus to the edit form heading after
the detail loads. The focused form regression and deployed journey assert
that focus destination.
