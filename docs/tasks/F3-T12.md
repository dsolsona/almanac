## Outcome and non-goals

Implement [plan 0031](../plans/0031-slo-eligible-status.md). A newly created SLO
with complete due eligible measurements can be Healthy. Explain its evaluation
start, coverage and actual cutoff without confusing age with gaps. No collection
schedule, operator records, target defaults or historical compliance changes.

## Acceptance and expected cases

- Existing SLI with nine 99/100 observations; a new 98% SLO has 50% observed budget
  remaining and 0.5x burn once its due eligible observations exist. Complete,
  fresh eligible coverage permits Healthy before a full rolling window exists.
- Before the first interval's deadline, show Waiting for data. A due absent
  interval remains missing/partial; all-absent data cannot be Healthy.
- Advancing wall time while collection stops produces incomplete/stale status;
  a received-observation watermark cannot freeze the horizon.
- A 99.9% target retains 10x burn and -900% observed budget on the same counts.
- Default current/detail/list and API/CLI evaluation use coherent disclosed bounds;
  explicit historical endpoints and daily compliance retain their contracts.
- Navigate list → detail → back in normal isolated deployment. Preserve chart/list
  geometry, keyboard access, both themes and mobile states from the retained reference.

## Implementation evidence

Original runtime diagnosis: a new SLO starts at creation; shortened
eligibility forces `incomplete_coverage`, and due-but-not-yet-collected intervals
were included through the current cadence boundary. The accepted correction is
recorded in ADR-0043. No operator records were changed during investigation.

Initial regression evidence: `make test` first failed because `LatestDueEnd` did
not exist. The deterministic deadline helper and urgency changes then passed the
fast gate (444 frontend tests). Added UI regression fixtures initially needed a
missing required `snapshot_id`; after correcting that fixture, both new assertions
failed as intended: missing evaluation/coverage explanation and the old No data yet
label. The PostgreSQL current/default-vs-canonical parity regression is now running
against the pre-correction current evaluation implementation.

Implementation ruling: accept whole observations that already arrived before the
fixed completion deadline, while the clock remains the minimum advancing cutoff.
This preserves useful available data and existing deterministic fixture values;
it cannot hide a collection outage by freezing at the last receipt.

The first full `make check` passed the fast gate (446 frontend tests) and then
failed storage integration (81.070 s): the new tail query referred to `interval_end`,
which is derived from start plus cadence in the merged schema. Corrected the SQL
source to use that canonical expression and regenerated sqlc output. No checks
were relaxed. Deadline expiry is rounded to the existing snapshot cadence tick,
so due-work publication and read invalidation advance together without a polling
loop or phase-boundary stale-cache interval.

The next full gate passed fast checks and the new nine-observation regression,
then exposed legacy oracle/fixture expectations and one real sparkline issue
(storage 107.109 s). Updated the independent raw oracle to select the due cutoff
from its own facts, retained the three-group fixture with an actual missing interval,
and corrected the open sparkline endpoint to evaluate its historical timestamp
instead of copying a live summary whose measurement cutoff may be earlier.
Historical series/daily comparisons remain exact; pending source work leaves a
gap in the sparkline without blocking a usable current summary.

Checkpoint `make check` passed storage integration (120.008 s), 446 frontend
tests and all 82 browser checks (2.2 min). Independent read-only review found
three remaining defects: live/explicit prepared-cache collisions, cached freshness
surviving its mid-tick deadline, and unavailable zero-count coverage receiving the
waiting message. Both cache request orders and a one-microsecond freshness expiry
were reproduced in storage (118.759 s); the unavailable-copy regression also failed
in the fast suite (446 other frontend tests passed). Corrections use private cache
metadata, retain the schema and public wire shapes, and apply expiry to current,
overview, service-summary, scheduling, consistency and metrics readers.

Final local `make check` passes: 447 frontend tests, storage integration in
116.434 s, and 82 browser cases in 1.9 min, approximately six minutes including
the fast gate, generation parity and production build. Independent follow-up
review reports all three findings resolved and no additional actionable findings.

Sequential `make test-e2e` passes all 16 real-container journeys in 5.4 min
(approximately 370 s including setup/build). The new 98% SLO starts Waiting,
then becomes Healthy with exactly 50% budget and 0.5x burn. Existing 99.9%
collection retains -900% and 10x; agent replacement and backend restart pass.
The new journey checks both themes at 1440 and 360 px, without horizontal
overflow. Actual screenshots were compared with the approved SLO detail mock:
left navigation, status/timeline/definition order and shared chart lanes remain;
the status explanation adds the approved eligibility/cutoff/counts. Mobile
stacks those existing sections. No operator deployment or data was changed.

The 35-day browser performance benchmark and published-head CI remain pending.
