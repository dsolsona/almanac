## Outcome and method

Separate PostgreSQL execution and runnable CPU wait in the remaining overview
latency before selecting another change. Separate-client browser acceptance is
pending hardware; it does not block server attribution. Preserve application
contracts, full-workload failures and the retained isolated stack.

The first private probe uses the actual generated query through pgx's normal
statement cache. One/eight/eight/one-reader cohorts each perform six rounds against
one exported repeatable-read snapshot and fixed evaluation time. Compare exact
ordered output hashes; retain initial custom and subsequent generic plan counts.
Sample each backend's own Linux scheduler counters immediately before/after its
query, outside the client query timer. Record both sampler round-trip durations
and the bracket duration: counter deltas include sampling/network gaps and cannot
be labelled exact SQL CPU time. Counters distinguish executed time from runnable
runqueue wait; neither covers pool admission, Go handling or complete API latency.

Use the retained F4-T20 image/fixture with ongoing background repair, no new
synthetic writer or browser workload. Ninety-second global deadline, one-second
statement timeout, 250-ms lock timeout and bounded cleanup. Read-only transactions
always roll back; credentials remain private in the launcher environment and
errors expose type/SQLSTATE only. Stop and retain failures rather than retrying.

## Acceptance and checks

- Every sample has 21 rows (20 plus lookahead), identical ordered values and

- Exact source hashes, fixture/image identity, plan counts, counter overhead and

  JSON validation and whitespace checks. No unrelated application suites.
