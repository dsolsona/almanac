## Outcome

An operator can schedule and inspect an exclusion for selected SLOs, correct it
through the authorized lifecycle actions, and inspect the same historical
evidence on the affected SLO. This stage presents calculation and audit effects.
Service-wide scope and automatic notification suppression follow later.

## Accepted API contract

All paths below are relative to `/api/v1`. Use the existing authenticated
session and CSRF checks, RFC 9457 errors, strict JSON decoding, and a caller-owned
`Idempotency-Key` on every write. Revision strings are canonical decimal values
within the signed 64-bit range. Scope uses canonical UUIDs.

| Method and path | Input | Success |
| --- | --- | --- |
| `GET /maintenance` | `limit`, opaque `cursor` | 200, latest revisions in creation-time/UUID order, including tombstones for history |
| `GET /maintenance/{id}` | Optional `revision`, omitted for latest | 200 with the selected revision and its strong ETag |
| `POST /maintenance` | Title, reason, UTC start/end, explicit SLO IDs | 201 with `Location`, ETag and created revision |
| `PUT /maintenance/{id}` | Same fields as create, current `If-Match` | 200 with a new revision |
| `POST /maintenance/{id}/end` | UTC end, reason, current `If-Match` | 200 with a new prospective end |
| `POST /maintenance/{id}/cancel` | Reason, current `If-Match` | 200 with the cancelled revision |
| `POST /maintenance/{id}/withdraw` | Reason, current `If-Match` | 200 with the withdrawal revision |
| `GET /slos/{slo_id}/maintenance` | UTC start/end, `limit`, opaque `cursor` | 200, current effective windows overlapping the requested range |

The proposed resource shape is `id`, `revision`, `title`, `reason`,
`start`, `end`, `slo_ids`, `creator_id`, `actor_id`, `operation`,
`created_at`, `updated_at`, `audit_id` and `tombstone`. Use
`"maintenance:<id>:<revision>"` as the strong ETag. Preserve operation on
tombstones so clients can distinguish cancellation from withdrawal. Time-based
display status uses the evaluation time and stored bounds.

Use `items` and optional `next_cursor` for pages. The general list uses the
existing maintenance cursor, with default 50 and maximum 200. The SLO overlay
query uses an indexed SLO/interval lookup with strict half-open overlap
(`window.start < end && start < window.end`). Bind its cursor to SLO and range.
Return original bounds so inspection explains clipped spans. A withdrawn or
cancelled window remains visible in audit history and drops out of the active
exclusion overlays.

Validation maps malformed bodies and headers to 400, inappropriate session or
role to 401/403, absent IDs or revisions to 404, and stale revisions or
idempotency conflicts to 409. A revision conflict includes the current revision.
An unaligned interval returns a typed problem with affected SLO IDs and both
suggested UTC bounds when available. The caller must explicitly resubmit any
suggestion. An aligned, prospective end must preserve elapsed coverage.

## Implementation and verification

- Reuse `internal/storage/maintenance.go` for list, detail and commands.
  Writes already commit audit, authority and invalidation together. Keep the
  backend transaction clock authoritative for role and time checks.
- Add the indexed overlay projection and test adjacency, overlaps, revision
  changes, tombstones and cursor scope with PostgreSQL. The general maintenance
  list cannot serve as the SLO overlay query because it pages unrelated windows.
- Define requests, responses and errors in `api/openapi.yaml`, regenerate Go
  and web clients, and connect the ordinary authenticated backend router.
- Verify viewer/write boundaries, CSRF, exact replay, stale revision recovery,
  scheduled activation and preserved elapsed coverage on the deployed API.
- Connect the CLI and the reviewed UI with server-provided records, then verify
  normal authenticated browser navigation, calculations and graph inspection.
  Retain the 10/20-row UI page size and SLO page performance gates.

The accepted exclusion arithmetic and permissions remain the basis for implementation. Service scope and notification delivery are separate contract decisions.

## API verification

The ordinary backend routes now expose the accepted explicit-SLO API. The
HTTPS executable journey through the UI proxy and real PostgreSQL passed in
22.464 seconds, including CSRF, alignment suggestions, create replay, stale
revision, history, cancellation, prospective end, withdrawal and overlap.
The focused PostgreSQL overlay test passed in 0.668 seconds. It exercised
adjacent pages, rejection of cross-range and cross-SLO cursors, and edited scope.
The backend HTTP tests and application build also passed.

The first executable run exposed a test-order issue. Running maintenance
mutations before the existing legacy CLI/API comparison advanced the exclusion
authority halfway through the comparison. The fixture now completes that
comparison before testing maintenance. The operational calculator remains the
maintenance-aware path.

The management CLI and production UI are the next consumers. Backend claim
and delivery behavior, full browser acceptance and operational page performance
remain separate from the verified API increment.

CodeRabbit follow-up accepts UTC fractional timeline bounds through microsecond
precision and binds the exact precision to cursors. Migration 0069 adds a
partial GiST overlap index on non-tombstoned revision intervals. The query
retains the SLO membership index and filters to the current revision before
keyset ordering. Six populated upgrade checks and the fractional cursor/scope
check passed. The first migration test run exposed a synthetic downgrade
fixture that removed the migration ledger row but retained its index. Updated
fixtures remove the index and count the additional forward migration.
