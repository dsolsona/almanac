## Outcome and interfaces

Use existing `AlertPolicyForm`, `AlertOccurrenceList` and `AlertOccurrenceDetail`
with actual protected reads/commands and shared controls/charts. Add the Alerts
navigation/route, saved policies and create/edit flows; preserve current forms and
clear pending/error/empty states. Never fabricate an occurrence, numeric point,
acknowledgement or recovery. Reconcile uncertain commands with their original key.

Backend support must precede consumers:

- Window response adds server-derived bad count, observed/allowed error rate and
  burn display values from immutable saved counts/target through the existing
  shared `slo.CalculateOccurrences` mathematics. Display rounding cannot change
  the stored condition outcome. The browser does not calculate SLO/burn values.
- Alert list adds server-side `evidence` and `minimum_duration_seconds` filters.
  Matching means latest committed policy truth is breaching; unavailable recovery
  means indeterminate; waiting means open work deferred for calculation, distinct
  from source quality. Duration uses effective opening/terminal times and the
  request clock for open occurrences. All filtered totals/groups use the same
  repeatable-read query. Cursor identity binds filter values, not changing now.
- Group responses include the complete filtered firing count; never count just
  the current page. Preserve 10/20 UI paging and ordinary server-bound cursors.
- Interactive chart series must come from immutable retained evaluations with
  actual cutoffs and explicit gaps, as in the public proposal; no synthetic curve
  through missing/compacted/pending history.

Frontend source: `web/src/alerts/client.ts`, adapters, `AlertsPage.tsx`, existing
alert components, authenticated route/navigation and corresponding focused tests.
OpenAPI changes regenerate Go/web types; SQL changes regenerate SQLC. Keep CLI
parity synchronized after its independent F4-T38 stream is integrated.
