## Outcome and scope

Atomically replace a local password verifier, invalidate all existing user sessions,
issue a fresh session and, for the initial owner, complete onboarding. This is an
internal storage operation. Public API, password proof, plaintext policy, throttling,
cookies/CSRF, startup, CLI/UI and recovery remain subsequent application work.
Personal tokens and challenges do not exist yet; their future verification must
bind credential revision and their invalidation must be integrated before exposure.

Own `internal/storage/password_rotation.go`, focused unit/integration tests,
`internal/storage/query/password_rotation.sql` and generated dbgen output. Reuse
existing session helpers; narrow helper changes are allowed where necessary, with
existing session behavior preserved. No schema migration or dependency change is
needed. Coordinator owns documentation and Git operations.

```go
type RotatePasswordInput struct {
    CurrentSessionVerifier [32]byte
    ExpectedCredentialRevision int64
    ExpectedCredentialEpoch string
    NewPasswordVerifier string
    NewSessionVerifier [32]byte
    Now time.Time
    RequestID string
}
func RotateLocalPassword(ctx context.Context, databaseURL string, input RotatePasswordInput) (SessionAccess, error)
```

The application caller must prove the current password against the captured
revision/epoch, require different new plaintext, call ValidateNewPassword and hash
outside database locks. This function accepts only a supported encoded password
verifier and session digests. It cannot detect identical plaintext with a new salt;
never claim it alone implements the full password change contract.

## Validation and transaction

Require positive expected revision, canonical lowercase UUID epoch, nonzero Now,
valid UTF-8 nonempty RequestID at most128bytes, and strict supported new verifier.
Reject identical current/new session digests before any write. Invalid input returns
ErrInvalidSessionInput, rejected authority ErrInvalidSession. Errors use existing
safe operational wrapping without passwords, verifiers or database credentials.
Require the explicitly upgraded current schema; no implicit DDL.

Read owning user ID from the current digest, then begin a bounded transaction.
Lock installation FOR UPDATE, user FOR UPDATE and current session FOR UPDATE in
that order; do not upgrade a prior shared installation lock. Reuse existing expiry,
enabled-user, provisioned-installation, ownership, epoch and revision checks under
locks. Missing rows, expired or pre-creation sessions and stale proof revision/epoch
fail closed. Validate a supported current local password verifier. Reject an exact
match of the old and new encoded password strings as ErrInvalidSessionInput.

While onboarding is incomplete only bootstrap_admin_id may rotate; require that
initial user to remain an enabled admin. Other users cannot complete onboarding.
After completion, any enabled local user with valid authority can change their own
password, including users with a restricted session. Guard revision overflow by
failing without mutation; never wrap or reset it.

In one transaction replace the verifier, increment credential_revision once, clear
must_change_password and update updated_at. Delete all sessions belonging to this
user, then insert one fresh unrestricted session with the new digest, current epoch,
new revision, and supplied Now for created/last-seen time. Do not reuse any existing
session digest: check for a collision before deleting old sessions, including one
belonging to this user. Existing uniqueness also protects concurrent insertion.
Preserve other users and their sessions. Use PostgreSQL microsecond precision.

For initial completion set onboarding_completed_at to Now in the same transaction;
later changes preserve this timestamp. Preserve installation ID and credential epoch.
Insert identity.password.changed and identity.session.issued success audits; initial
completion additionally inserts identity.onboarding.completed. Actor and subject
are the user UUID; only server time and RequestID accompany them. Any write/audit
failure rolls back password, revision, sessions and completion marker together.
Return the fresh SessionAccess only after commit, with current role and the normal
30-minute idle/12-hour absolute lifetime. There is no hashing under locks.

## Acceptance checks

1. Initial owner rotation replaces verifier, increments revision, clears required
   change, completes onboarding once and returns a usable unrestricted session.
   All old user sessions fail authentication, including a second restricted session.
2. Normal rotation preserves the completion timestamp, installation ID/epoch and
   other users/sessions. Verify exact audits for first and subsequent rotation.
3. Two simultaneous initial rotations produce one winner and one invalid-authority
   result; exactly one fresh session and one set of completion audits survive.
4. Unknown, revoked, expired, pre-creation, disabled, stale epoch/revision, missing
   installation and non-owner pre-onboarding attempts fail without writes or audits.
5. Malformed new verifier, same encoded verifier, same current digest, collision with
   another existing session (same user and another user), and revision overflow leave
   all state unchanged. Duplicate digests must never resurrect old credentials.
6. Inject audit failure at completion to prove every preceding mutation rolls back;
   remove the fault and retry successfully. Fault injection is test-database-only.
7. Observe a genuinely blocked row lock, cancel, verify bounded return and retry.
   Coordinate concurrency with bounded contexts and joins, not sleeps or busy loops.
8. Missing/pending/newer schema and unavailable DB fail closed with redacted errors.
   Pure invalid inputs have focused unit coverage. Keep prior session tests intact.
