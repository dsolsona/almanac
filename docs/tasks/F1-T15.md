## Outcome and boundaries

Run `almanac setup` noninteractively against the real HTTPS authentication backend,
using protected initial/new password files and the same cookie/CSRF operations as
the UI. Complete mandatory initial rotation without database access from the CLI.
Exercise the accepted uncertain-response behavior in a client. No general login,
persisted profiles/session files, token issuance, recovery, management, UI screens,
combined mode, new dependency or database migration in this increment.

Coordinator choices within the accepted setup contract: explicit connection flags
for this first command; in-memory cookies only; no session secret in output; best-
effort logout after a definitive result. Profiles and reusable CLI login follow
separately. Never turn cleanup failure into a claim that rotation rolled back.

## Command and output

Add `setup(ctx,args,stdout,stderr) int` in `internal/command/setup.go`, wire Run/help,
and preserve existing commands. Accepted flags:

| Flag | Behavior |
| --- | --- |
| `--backend-url` | Required canonical HTTPS origin, no path/query/fragment/userinfo |
| `--initial-admin-login` | Required UTF-8 login, 1–256 bytes |
| `--initial-admin-password-file` | Required protected regular file, at most512 bytes |
| `--new-password-file` | Same protection and512-byte bound |
| `--ca-file` | Optional public regular PEM CA bundle, at most64KiB |
| `--timeout` | Whole operation deadline; default30s, positive and at most2m |
| `--output` | `text` default or `json`; reject other formats/positionals |

Use existing secretfile readers, including opened symlink-target/FIFO semantics.
Validate/read all inputs before any network action. Password bytes are valid UTF-8
and never trimmed, including final newlines. Reuse identity password validation for
the new password and reject an unchanged password locally; backend policy remains
authoritative. Never accept plaintext password arguments, stdin prompts or a TLS
verification bypass. This command does not load serve config or implicit profiles.

JSON stdout is exactly one versioned document plus newline. Success:
`{"schema_version":1,"operation":"setup","completed":true,"session_cleanup":"complete"}`.
If rotation definitely succeeded but logout failed, keep completed=true and set
session_cleanup=`unknown`, with a safe stderr diagnostic. No session secret is saved.
Errors use `schema_version`, `operation` and an `error` object containing stable
`code`, safe local `message`, `outcome_unknown` boolean and `session_state` enum
(`anonymous`, `restricted`, `authenticated`, `unavailable`, `unchecked`). Optional
validated request_id and retry_after_seconds may accompany errors. Never echo raw
server messages/bodies, network errors, paths, passwords, cookies, tokens or URLs.
Human success goes to stdout; diagnostics go to stderr. Honor output-write failure.

Exit0 success;2 local input/validation or server422;3 authentication/authorization;
5 already-complete/conflict;6 timeout/cancellation;1 other remote/protocol/internal
failure. Uncertain mutations use code=`outcome_unknown`, retain the boolean even
when exit6 applies, and explain that the initial/new password may already be active.
Never print success after an uncertain password response merely because context is
authenticated. Unknown flags and usage errors follow the existing JSON request
detection convention. Required flags are explicit; no secret environment values.

## Client boundary

Enable the pinned oapi-codegen client output in `api/oapi-codegen.yaml` and regenerate
`internal/api/generated.go`. Use generated request builders/client operations and
generated AuthResponse/Problem shapes; do not hand-edit generated files or duplicate
HTTP payload models. No new package dependency.

Create `internal/setupclient/client.go` and focused tests. Public internal interface:
`New(Options) (*Client,error)`, `(*Client).Complete(context.Context,initialPassword,
newPassword string) (Result,error)`, and `(*Client).Close()` for idle transport cleanup.
Options: BackendURL string, Login string, CABundle []byte. Result: Completed bool and
SessionCleanup string. Typed `Failure` carries Kind, stable Code, safe Message,
OutcomeUnknown, SessionState, RequestID and RetryAfterSeconds. Define `Kind` as a
string enum: invalid (exit2), authentication (3), conflict (5), cancelled (6), remote
(1). OutcomeUnknown is independent of Kind. Constructor validates configuration but
performs no network I/O. Never include
options/credential values in errors or log them.

Own a dedicated net/http transport, bounded response reader (64KiB, reject overflow),
in-memory cookie jar and verified TLS1.2+. Use system roots; append a valid optional
CA bundle, failing if no certificates can be parsed. Explicitly refuse redirects
(including same-host redirects), preserve request cancellation and close response
bodies/idle connections. Bound dial and TLS handshake to5s and response headers to10s,
subject to the command's overall deadline. Do not automatically retry any operation,
set Idempotency-Key, or rely on generated unlimited body parsing. Send Origin equal
to BackendURL, application/json and the correct CSRF token. No ambient HTTP proxy
configuration in this initial explicit-connection client.

Sequence: anonymous context → initial login → require restricted session → password
change → require valid normal-session success response → one logout attempt. Consume
the CSRF tokens and protected cookies returned by each operation; do not mint them
client-side. If login returns a normal session, report setup_already_complete/conflict
and do not rotate an ordinary password. Best-effort logout also follows a definitive
post-login rejection; it cannot replace the original error. No persisted client state.

Validate successful response shape in addition to decoding generated types: require
csrf_token and session keys, explicit restricted boolean for non-null sessions, and
nonempty user_id/login/role. Login/setup sessions must be administrator; reject a
restricted non-administrator without rotation. Password success must preserve the
same user ID and explicitly report restricted=false. Require the expected preauth
or session cookie with Secure, HttpOnly, SameSite=Lax, Path=/ and no Domain; reject
ambiguous/invalid cookie values. Fresh anonymous context must explicitly contain
session=null. Missing fields/cookies are protocol failures, not zero-value success.

For a transport error, truncated/oversized/malformed response, any5xx (including a
well-formed503 authentication_unavailable), or unexpected response after submitting
login/password change, preserve an unknown outcome. A lost database COMMIT acknowledgment
can be reported as503 after the mutation has committed. Never repeat the
mutation, continue to password change after uncertain login, or announce completion.
If the original operation context still permits I/O, make at most one context request
to report current session state. If cancelled/expired, report unavailable/unchecked
without extending the deadline. Context failure keeps the outcome unknown. Do not
perform logout or other mutations after uncertain login/password change.

Only recognized documented precommit status/code pairs are definitive rejections:
401/unauthenticated,403/origin_rejected or secure_transport_required or csrf_invalid,
409/session_present,422/password_unchanged or password_policy,429/rate_limited,
400/invalid_request,405/method_not_allowed,408/request_timeout,413/request_too_large,
415/unsupported_media_type and501/capability_unavailable. The explicit501 admission
rejection is the exception to5xx uncertainty. Map these to safe local messages;
unexpected pairs after mutation use outcome_unknown. A request ID is only exposed
if it matches the server's32-lowercase-hex
format; retry seconds must parse as a positive integer. Unknown/untrusted response
fields must never leak into output. TLS/connection failure before anonymous context
has no uncertain mutation. Context lookup itself never establishes rotation success.

## Acceptance and checks

1. Command tests cover required/unknown flags, JSON/text output, exit mappings,
   cancellation, bounded password/CA files and validation-before-network. No stdin
   read, output secret, path/URL disclosure or client-state file is created.
2. Verified TLS boundary tests cover trusted custom CA success, untrusted certificate,
   HTTP/noncanonical origins, redirect refusal without credential forwarding, bounded
   bodies and explicit cancellation. Use real TLS test servers; no InsecureSkipVerify.
3. Fault-server tests count each route: lost login and lost password responses perform
   no automatic replay/follow-on mutation; context checked at most once if time remains;
   authenticated context never changes unknown into success. Cover failure before/after
   response headers, malformed/missing-field success, well-formed503 after mutation,
   wrong/missing cookies, 429/no retry, and expired operation budget.
4. Real PostgreSQL/backend/executable CLI acceptance provisions initial owner, runs
   JSON setup through verified TLS, confirms rotated credentials and completed state,
   revokes the temporary successful session, and proves a second setup with ordinary
   credentials refuses rotation. Server restart preserves state. Use disposable fixture
   databases and ephemeral ports, not the maintainer preview or external services.
5. Preserve existing backend ownership/drain acceptance and UI-only smoke. Add fixed
   setupclient package selection to unit/race lanes; integration remains the existing
   serial command/storage/service/HTTP packages. Full Go gate compiles tagged tests
   before coordinator execution. No generic command passthrough or alternate runners.
6. Coordinator runs actual integration, integrated full gate, race and docs checks;
   independent reviewers inspect behavior/evidence. No browser/setup-profile or full
   F1 completion claim. Update README/help/spec implementation notes in the same change.
