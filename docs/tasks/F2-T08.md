## Outcome and non-goals

An unrestricted administrator can list agents, register one, view its one-time
token, inspect its metadata and credential history. Registration works before an
agent connects. Rotation/revoke/disable forms are the next bounded increment;
do not add nonfunctional controls for them. No fabricated health, connectivity,
capabilities, setup snippets for an undelivered binary, datasource UI or CLI.

## Screen behavior

- Agent list defaults to50 records. Use real name/display name, enabled/disabled
  administration state and exact UTC timestamps. No per-row credential fetching or
  inference that enabled means healthy. Clear empty/loading/error states; failed
  refresh may retain data only with stale label and last successful fetch time.
- Share detail via `?agent=<canonical UUID>`; use `agents_cursor` and
  `credentials_cursor` for bounded opaque cursor state. No secrets or command keys
  in URLs. Respect back/forward/reload. Keep one list and one history page, not an
  accumulating cache; no fetching all pages. Invalid IDs show a safe error.
- Detail shows metadata and independently paginated credential history, including
  exact issued/expiry/retirement/revocation timestamps. Explain scheduled retirement
  separately from revocation. Never infer current-epoch liveness from this DTO.
- Register uses shared Dialog with name, display name, optional lifetime and
  current-password fields. Labels: Agent name, Display name, Lifetime (seconds),
  Current password. Action: Register agent. Respect server defaults and bounds,
  preserve safe fields on error, and never silently normalize text. Prevent double
  submission. Clear password after every dispatched attempt; require reentry.

Use shared Button, Panel, TextField, LoadingIndicator, Dialog and existing theme
tokens. Heading font remains Bevan; body/table values use system sans/monospace.
Feature CSS owns layout only. Wide tables are named keyboard-accessible scroll
regions; no page-wide overflow at360px, and coarse controls remain44px.

## Secret and outcome handling

Fresh create success presents a separate focused token Dialog, selectable text and
explicit Copy token action with announced success/failure and manual-copy fallback.
It is shown once. Keep token only in ephemeral component state; clear on every
close path (button/Escape), navigation, logout, authority loss and unmount. Do not
leave hidden token DOM, log it, snapshot it or put it in a generic notification.
Copy only on user gesture. Restore focus to a live meaningful control after closing.

Use crypto.randomUUID once when the user submits a new intent. For uncertain
outcome, retain the original semantic fields/key in memory, show Outcome unknown,
and offer explicit Retry registration with fresh password. Never generate a new
key or automatically repeat after auth refresh. A replay has unavailable token;
say so accurately and show returned agent/history. No invented retrieval or recovery
guarantee after reload. Successful creation refreshes the real list/detail.

401 triggers the owning recheck and fresh-password retry only if the session still
has authority; it does not itself prove logout.403 clears unauthorized results.
CSRF failure permits recheck then deliberate retry.409 explains reconciliation
without silently changing an uncertain intent.429 disables resubmit until validated
Retry-After elapses with an accessible wait message. Errors use fixed safe copy.
Abort stale reads and ignore late results. Aborting a dispatched create retains
uncertainty unless the user explicitly abandons the in-memory intent.
