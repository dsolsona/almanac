## Outcome and acceptance

An editor/admin changes a datasource from a lost agent to a replacement. The
replacement immediately becomes assigned and both agents get new configuration;
an old agent reconnecting no longer receives that datasource. Every subsequent
old-agent submission is rejected, including buffered observations and receipt
replay. Accepted history and measurement revisions stay intact.

The UI shows Updating until the replacement acknowledges configuration, then Active
with diagnostics available. Configuration completion takes a few seconds on a
connected agent and is independent of measurement freshness. Another assignment
can recover a failed replacement. No old-lease deadline blocks recovery.
Editors cannot change connectivity/credentials, and viewers cannot change assignment.

## Reproduction and scope

On the base revision, `handleDatasourceReassignment` retains the source assignment;
`ListReadyDatasourceReassignments` and the reconciler both require drain or recorded
expiry before activating the replacement. Completion then deletes the pending row
before replacement collection. Existing integration fixtures assert that policy.

Scope includes storage/query/migration, ingestion fencing before receipts, generated
contracts, editor authorization and agent summaries, datasource UI and CLI, specs,
unit/integration regressions and the real isolated Compose journey.

### Returning assignment and unavailable destination follow-up

Local retesting exposed an agent transition rejection when an already installed
SLI returned with a new ownership start. Directly resetting the database assignment
left the running agent's prior configuration installed; reassignment then changed
both the datasource version and canonical ownership start. The agent rejected that
as a changed collection and repeatedly reconciled before sending another heartbeat.

Focused Go regressions reproduced `transition changed an existing collection`
both in transition classification and through WebSocket configuration notices.
The correction permits ownership-start metadata changes as withheld additions:
configuration can be acknowledged immediately, while collection still requires a
matching new execution grant. Query and measurement-definition changes retain
existing rejection checks.

A subsequent move to the unavailable original agent was already assigned correctly,
but the generic Updating heading obscured the actual blocker. Show Not collecting
and Agent unavailable for that state; preserve pending configuration evidence until
that agent acknowledges it. Do not label an offline destination Active or restore
the prior assignment automatically. Final verification and local rebuild are pending.

The maintainer clarified pending-return semantics in ADR-0039: restoring the source
cancels the operation immediately, with fresh configurations and authorization floors
but no reverse pending row. The existing local reverse operation was cleared and
audited without changing its restored assignment or configuration revisions.

Independent review identified an ACK/cancel race because completion does not change
the configuration version. A focused database regression reproduced a stale cancel
being accepted as a fresh reverse move. Explicit cancellation intent on PUT now
requires a matching pending move; a completed move conflicts without mutation and
the UI refreshes that result. This preserves uncertain-write reconciliation and
prevents an automatic reverse operation from stale page state.

The cancellation regression failed with a reverse pending row before the fix and
passed afterward (isolated storage: 0.359 seconds). The ACK-race extension failed
because stale cancellation returned success, then passed with conflict and no
assignment change (0.296 seconds). The corresponding frontend race failed with
Updating retained, then passed with automatic refresh. Optional cancellation intent
was regenerated from OpenAPI and passed through the HTTP handler, without changing
normal writes or GET-based uncertain-outcome reconciliation.

Read-only review confirmed matching pending validation occurs before transfer
mutations under the existing agent/datasource locks. UI conflict refresh retains
request/route cancellation guards. No new actionable findings were reported.
The local app and agent were rebuilt with the initial cancellation/ownership-start
fix and passed host HTTPS readiness. The final ACK-race handling is undergoing
full verification before the final local rebuild. The datasource remains on the
maintainer-selected agent; no further assignment reset was performed.
