## Outcome and boundaries

Provide the browser's typed same-origin authentication operations before wiring
screens. Use existing generated TypeScript request/response models, browser-managed
HttpOnly cookies and in-memory CSRF context. No new dependency, API, backend change,
session/password storage, login redirects, UI component or production entry-point
change in this task. This is a prerequisite in the browser onboarding increment;
its unit tests do not establish a working browser/backend/database journey.

Own `web/src/auth/client.ts` and `web/tests/auth-client.test.tsx`. Keep all other
files coordinator-owned unless a concrete blocker is reported. Existing approved
unit selection accepts the .test.tsx suffix even for client-only tests.

## Interfaces

Import `components` types from `../api/generated.ts`. Export aliases `AuthContext`,
`LoginInput` and `PasswordInput` for AuthResponse, LoginRequest and PasswordRequest.
Export `AuthOptions = { signal?: AbortSignal }` and `AuthFailure extends Error` with
readonly fields `kind: 'rejected' | 'unavailable' | 'uncertain'`, `code: string`,
`recovery: AuthContext | null`, and `retryAfterSeconds: number | null`.
The message/code are safe local values. Recovery context contains sensitive CSRF
state for the caller's memory only; never log/serialize it into a diagnostic.

Export `createAuthClient(fetcher?: typeof fetch)` returning these methods:

- `context(options?: AuthOptions): Promise<AuthContext>`
- `login(input: LoginInput, context: AuthContext, options?: AuthOptions): Promise<AuthContext>`
- `changePassword(input: PasswordInput, context: AuthContext, options?: AuthOptions): Promise<AuthContext>`
- `logout(context: AuthContext, options?: AuthOptions): Promise<void>`

The default fetcher is the browser fetch implementation; injection supports focused
fault tests, not alternate runtime endpoints. Use fixed relative `/api/v1/auth/`
paths with context/login/password/logout suffixes, POST, JSON bodies ({} for context
and logout), `credentials: 'same-origin'`, `mode: 'same-origin'`, `cache: 'no-store'`
and `redirect: 'error'`. The browser supplies Origin; do not try to override it.
Supply X-CSRF-Token for mutations from the supplied context. Never send
Idempotency-Key, cookies manually, credentials in a URL, or arbitrary caller headers.

## Response and deadline behavior

Each public operation owns a 30-second deadline, including any recovery read, and
honors caller cancellation. Clear timers/listeners on completion; cancellation
also bounds body reading. Read at most64KiB, counting actual bytes, then decode JSON.
Reject malformed/oversized responses without retaining raw bodies/errors in public
failure fields. No generated unbounded parser or new schema-validation library.

Validate successful AuthResponse shape at runtime: explicit csrf_token string
nonempty, explicit session null or object, nonempty user_id/login/role strings,
and explicit boolean restricted. Do not convert omitted/null restricted into false.
Login success requires a session. Password success requires a normal session with
the same user_id as the supplied context; a missing current session is rejected
locally before I/O. Logout success requires204 and no body. Browsers cannot inspect
HttpOnly Set-Cookie; do not implement JavaScript cookie inspection or persistence.

For login/password transport loss, invalid success shape/body, redirects, unexpected
status/code pairs, or5xx, throw `kind:'uncertain', code:'outcome_unknown'` even when
a later context says signed in. If the original deadline/caller signal still permits
I/O, attempt at most one context read using that same budget. Attach a validated
result as recovery, otherwise null. Never repeat the mutation, submit another
mutation, refresh/retry indefinitely or announce password-change completion from
context alone. An already-cancelled operation before submission has no unknown
mutation; cancellation after submission retains uncertainty and performs no I/O
after its budget expires.

Only documented valid precommit Problem status/code pairs are definitive:
400/invalid_request;401/unauthenticated;403/origin_rejected,secure_transport_required,
csrf_invalid;409/session_present;422/password_unchanged,password_policy;
429/rate_limited;405/method_not_allowed;408/request_timeout;413/request_too_large;
415/unsupported_media_type;501/capability_unavailable. The explicit501 admission
rejection is the exception to5xx uncertainty. Require a valid generated Problem
shape before treating a rejection as definitive, including string request_id and
an array of correctly shaped field_errors. Map codes to safe local messages; do
not expose server messages, arbitrary fields, parser/network errors or raw bodies.
Only expose Retry-After when it is a positive safe integer number of seconds.

Context failures are unavailable/rejected, not an uncertain credential mutation.
Logout failure reports that sign-out could not be confirmed, without replay or
claiming the session ended. Screens can perform an explicit status check afterward.
Uncertainty messages explain that the operation could have completed and that the
user should check sign-in state or deliberately sign in again, without automatic
resubmission. A valid session alone does not prove the requested password change.

## Acceptance and checks

- AC1: Exact fixed requests, JSON/generated shapes, CSRF, credentials/cache/redirect
  policy and no Idempotency-Key. Normal context/login/password/logout results work.
- AC2: Reject missing/null/wrong-typed fields, absent login session, restricted or
  different-user password success, oversized/truncated/malformed body and redirects.
- AC3: Lost login and password responses each issue the mutation once and at most
  one recovery read; no follow-on mutation. Signed-in recovery stays uncertain.
  Valid503 and malformed Problem remain uncertain; documented429 is definitive and
  carries safe retry seconds without retry. Unknown status/code combinations fail
  conservatively. Verify no raw response/password content in user-facing messages.
- AC4: Fake-time deadline/cancellation tests cover a pending request and pending
  body, no recovery once the budget expires, caller cancellation, and timer/listener
  cleanup. Use explicit barriers rather than tight wall-clock scheduling assumptions.
- AC5: Focused unit checks, existing complete web/Go gate and independent diff
  review. Real browser/API/database acceptance follows in the dependent screen task;
  do not substitute these fault stubs for that evidence.

Use only existing approved make families; no new command approvals, new dependencies,
generic wrappers, Git mutations, nested agents or database fixture access. Coordinator
owns docs/Git, integrated checks and publication. Write focused failing tests, run
`make verify VERIFY_MODE=unit TEST_FILE=tests/auth-client.test.tsx`, then report exact
counts/results/first failures and freeze. Do not mark the task accepted or start UI.
