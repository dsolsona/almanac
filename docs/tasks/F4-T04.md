## Outcome and evidence

Opening an SLO during dirty-hour preparation must retain compatible published
values, explicitly labelled stale/failed with their original generation. It must
not claim Healthy, silently refresh provenance or turn normal navigation into a
503/retry loop. When no compatible published result exists, disclose unavailable
calculation and preserve other usable panels. Authentication errors remain errors.

The 200-SLI run in F4-T03 reproduces repeated status 503 responses while all ten
browser journeys attempt details. `ReadCurrentSloStatus` recomputes a non-current
projection and propagates `ErrDerivedPending`; the list already retains labelled
last-known values. Verify that exact path against PostgreSQL before fixing it.

## Edit scope and acceptance

1. Add a real database regression for dirty preparation after a published result;
   verify retained exact values/generation, explicit lag and no Healthy inference.
   Cover failed preparation, incompatible revisions, no projection and recovery.
2. Add the same optional current-state metadata used by overview to the current
   status contract. Regenerate OpenAPI bindings. Update browser validation and
   the existing verdict/notice components, preserving layout and both themes.
3. Verify clock/freshness behavior remains canonical when calculations are ready.
4. Correct the contention harness to distinguish ten concurrent API users from
   rendered browser samples. SPEC-0019 sets these as separate requirements; do not
   alter its API or browser limits. Preserve all previous failed artifacts.
5. Repeat only the affected integration/frontend checks and measured deployment
   workload, including exact independent values and live-ingestion interference.
