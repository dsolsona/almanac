## Outcome and non-goals

An authenticated user can save, inspect, update, enable/disable and reconcile a
policy through the real API and equivalent CLI. Existing occurrence/evidence/
history/processing reads and global acknowledgement become accessible through the
same boundary. Follow the reviewed [public proposal](../design/alerting-public-contract.md)
as the implementation profile; keep its proposed status and full architecture
acceptance distinct from authorization to continue implementation.

Production worker activation, shared maintenance-calculation adoption and the
100/200-policy release gates remain open. This task does not claim a live firing
journey before those gates. The selected UI, archive impact and immutable chart
series remain delivery-plan work, not substitutes for these operations.

## Interfaces and edit scope

- Storage adds `UpdateAlertPolicy` and `EnableAlertPolicy`, returning the existing
  `AlertCommandResult`. Updates carry expected configuration version, optional
  name/severity/SLO/conditions and a reason; metadata preserves evaluation revision
  and original occurrence evidence. Semantic changes atomically supersede/cancel
  old work and start a new immutable revision. Enable starts fresh scheduling.
- Public commands use authoritative time after authority/resource locks; retained
  internal explicit-boundary callers remain supported. Rebinding locks affected
  SLI authorities in UUID order, then affected SLOs, policy, cursor and occurrence.
- Source contract: `api/openapi.yaml`; regenerate `internal/api/` and web types.
  Add typed alert schemas with snake-case fields, string versions/exact decimals,
  integer-second durations, UTC times and explicit unavailable reasons.
- HTTP: `internal/alerthttp/`; register management routes in backend HTTP, with
  session/CSRF/same-origin, request IDs, bounded strict JSON, strong ETags,
  actor-scoped command receipts and safe Problems. Do not serialize internal Go
  records directly or add a database path to the CLI.
- CLI: `internal/alertclient/`, `internal/command/alerts.go`; reuse protected
  profiles, generated client, cancellation and uncertain-response handling.

## Acceptance and expected cases

1. Create with fast 14.4×/5m/1h and sustained 6×/30m/6h: one persisted policy,
   no fabricated occurrence, API ETag/version and CLI reads agree. More than two
   conditions are accepted within the explicit profile.
2. Metadata update preserves current occurrence/evaluation revision; semantic
   update/rebinding and disable record distinct terminal causes and exact pending
   cancellation ranges. Enable creates a new revision without replaying disabled
   time. Lost-response replay returns the original committed result.
3. Viewer reads but cannot mutate; missing/restricted/expired sessions, missing
   CSRF, stale versions, duplicate headers/query keys, unknown fields, oversize
   JSON and malformed decimal/duration inputs produce safe actionable errors.
4. HTTP/CLI filters/group counts/page cursors and exact original/latest evidence
   reflect storage, with processing lag separate from lifecycle. Unknown commands
   remain unknown, expired keys cannot silently reexecute, and mutations do not
   automatically replay after transport failure.
5. Boundary clocks and receipt/session expiry are checked after lock waits; new
   source changes fence old claims. Source SLI/SLO activation semantics stay as
   accepted, independently of alert-policy activation.

User acceptance starts with a normal authenticated account and existing SLO;
create/list/get/update/disable/enable through the real backend and protected CLI,
including invalid input correction and uncertain-response lookup. Use the isolated
container deployment for the final executable journey; preserve operator data.
