## Outcome and scope

Administrators can rotate an agent credential, revoke a selected credential and
disable an agent from its detail page. These use the existing verified client/API,
shared controls and real resource versions. No connectivity claims, new endpoints,
CLI, provider work, dependencies or framework changes.

Read AGENTS.md, testing.md, ways-of-working.md, linked specs, design guidance,
F2-T08, existing browser client and actual shared controls before implementation.
Own feature source/tests under web/src/agents and web/tests, plus narrow AuthPage
state integration and its tests. Coordinator owns docs, Go and browser scripts.
Prefer a focused lifecycle component/controller over expanding registration's
already substantial renderer. Avoid a speculative generic mutation framework.

## Interface and behavior

- Retain the exact ETag returned by the selected agent detail GET, keyed to that
  resource/read result. Enable new mutations only with current successful detail
  evidence. Never reconstruct versions through JavaScript numbers.
- Rotation dialog: current password, optional lifetime seconds (blank/0 default,
  maximum31536000), optional overlap seconds (blank default600;0..600). Explain
  that the replacement serves the same identity and old credentials retire within
  the requested overlap. Backend remains authoritative about two-active limits.
- Revoke dialog identifies the credential ID and explains immediate revocation
  without deleting the identity. Disable dialog identifies the agent and explains
  revocation of all credentials and cancellation of future work. Require explicit
  confirmation/current password; no action on dialog opening. Already revoked or
  disabled records need no active destructive affordance.
- Capture one UUID command key, immutable target/semantic inputs and original
  strong ETag per dispatched intent. Retry uses the original key and ETag; replay
  precedes stale-version checking server-side. Never silently refresh an uncertain
  command to a different version or invent success from cached data.
- AuthPage owns safe intent across temporary anonymity; include initiating user ID
  and clear on explicit logout/confirmed identity change/explicit abandonment.
  Do not retain passwords, token, CSRF or authentication context in safe intent.
  Preserve an earlier unknown outcome when a later retry is rejected. Require
  deliberate retry with fresh password after successful authority reconciliation.
-409 shows reconciliation and explicit abandonment/new-command choice; no automatic
  resubmit.429 honors validated Retry-After.401/CSRF use the existing explicit auth
  owner; failure to confirm blocks privileged work.403 clears protected results.
- Fresh rotation token is ephemeral and shown once with copy announcement and all
  close/navigation/logout/unmount clearing. Replayed rotation has no token: explain
  accurately. Reuse the proven token presentation where appropriate, without
  conflating new rotation tokens with prior registration results.
- Refresh authoritative detail/history after accepted/replayed lifecycle result;
  receipt metadata may describe historical state. Display refresh failure as such.
  Do not overwrite a newer resource from an old receipt. Ignore late completions
  after selection change, abandonment, logout or identity change. No automatic
  mutation retry. Prevent duplicate and overlapping mutation submissions, including
  registration versus lifecycle actions, while a request is in flight.
